# Phoenix Literary Quality Standard

> 状态：正式版故事库强制规范  
> 适用范围：普通 Journey、特别 Journey、全库编辑审核、AI 内容生产  
> 最后整理：2026-07-31

Phoenix 的故事不能只是把景点知识放进第二人称导览文案。故事必须让 Explorer 遇见一个具体的人、一个需要处理的问题，以及一个会改变阅读者理解的过程。

本文件记录 2026-07-31 全故事库总编辑审核后确立的正式标准。它与 `STORY_GUIDELINES.md`、`CONTENT_QUALITY.md` 同时生效；如规则冲突，以 Founder 最新明确决定和 `AI_DEVELOPMENT_GUIDE.md` 的优先级为准。

## 1. 正式版故事定义

每个 Journey 的故事必须同时拥有：

1. 可辨认的主角或经过明确设计的叙述声音。
2. 主角当下想完成的目标。
3. 阻碍目标的冲突、误解、限制或选择。
4. 至少一次理解、情绪或行动上的变化。
5. 一个由前文行动造成的高潮或关键决定。
6. 一个能够回收人物、物件、动作或问题的结尾。
7. 只有当前地点、文化或幻想世界才能成立的内容。
8. 能自然生长出生词、发现、挑战与回忆的学习结构。

只有景色、历史事实、文化解释和保护结论，不构成完整故事。

## 2. 全库差异化要求

每次新增或修改故事，都必须把整个故事库视为同一本作品集进行横向检查。

全库必须保持：

- 开场机制不同
- 主角身份不同
- 叙事任务不同
- 冲突类型不同
- 情绪曲线不同
- 高潮动作不同
- 结尾方式不同
- 学习主题不同
- 主要意象不过度集中
- 教育意义不过度集中

不得连续建立以下模板：

```text
时间或天气
→ 你走进地点
→ 介绍历史与结构
→ 说明文化价值
→ 用保护或“过去与今天”升华
```

也不得让特别 Journey 连续依赖：

```text
神秘物件出现
→ 追踪异常
→ 得到过去或未来留言
→ 天亮时异常消失
```

## 3. 人物标准

普通 Journey 与特别 Journey 默认应有可辨认人物。

人物必须至少具备三项：

- 姓名或稳定称呼
- 具体身份
- 明确目标
- 个性或错误判断
- 与他人的关系
- 情绪变化
- 需要承担的后果
- 只有本人会说出的语言

主角不得只是移动摄像机。群体词语如“游客、工匠、居民、研究者”不能自动替代人物设计。

允许少量无名第一人称、物件视角或纯寓言叙述，但必须明确说明这种设计的文学理由，并保证其不成为批量模板。

## 4. 冲突与高潮

冲突不等于危险。可使用：

- 人与人意见不同
- 人物判断错误
- 信息互相矛盾
- 规则与现实发生冲突
- 个人愿望影响他人
- 传统用法与现代需要需要协商
- 数据不足，必须暂缓结论
- 恐惧、好胜、虚荣或偏见造成问题
- 不同年龄、能力或文化背景的人需求不同

高潮必须让人物做出行动或承担结果，不能只用一句“终于明白”代替。

## 5. 结尾标准

结尾优先回收：

- 开场出现的物件
- 人物最初说过的话
- 一个未解决问题
- 一次错误判断
- 一段关系变化
- 一个能够进入回忆页的具体画面

以下表达不可成为批量结尾：

- 不只是……而是……
- 真正珍贵的是……
- 让历史继续走向未来
- 保护的不只是一座建筑
- 过去与今天在这里相遇

保护、保存与文化延续可以作为少数故事主题，不能成为整个普通 Journey 库的默认教育意义。

## 6. Story 与 Discovery 分工

### Story 负责

- 人物
- 目标
- 场景
- 行动
- 冲突
- 情绪
- 选择
- 余韵

### Discovery 负责

- 年代
- 来源
- 数字
- 技术原理
- 文化解释
- 历史边界
- 事实与传说区分
- 进一步比较

Story 可以自然使用真实事实，但不得提前把 Discovery 的所有知识讲完。Discovery 不得只是把 Story 改写一遍。

## 7. 年龄与语言等级

中文能力等级与年龄不是同一维度。

- 低 Phoenix Level：降低句法、词汇与信息密度，不删除人物目标和因果关系。
- 高 Phoenix Level：增加证据、立场、隐含关系与表达深度，不把故事改成论文。
- 8 岁读者需要清楚行动、人物关系与可感知结果。
- 12 岁读者需要谜题、冲突、幽默、选择与成长。
- 16 岁读者需要复杂动机、真实性边界与可讨论问题。
- 成年学习者需要文化准确、语言自然及不幼稚的表达。

不得用幼儿化语气代替语言降级，也不得用抽象名词堆积代替高级内容。

## 8. Phoenix 学习闭环

正式故事必须顺畅支持：

```text
故事
→ 生词
→ 发现
→ 挑战
→ 留下印象
→ 盖章
```

要求：

- 生词实际服务人物行动与地点理解。
- 发现提供故事未讲完的新知识。
- 挑战既能检查语言，也能检查推断、动机、证据与选择。
- 留下印象能回忆一个人物、动作、选择或画面。
- 盖章代表完成一段经历，不只是读完资料。

不得恢复“思考／表达”为公开 Journey 步骤；相关提示继续作为独立能力与兼容字段使用。

## 9. AI 痕迹审核

人工与自动审核必须检查：

- 四段是否过度整齐
- 是否每段只承担一个模板功能
- 是否连续使用同一转折句
- 是否每篇都在结尾升华
- 是否缺少人物口吻、犹豫、错误和不完美表达
- 是否所有人物都理性、温和、正确
- 是否存在可以替换地点名后继续成立的句子
- 是否用抽象词掩盖没有事件发生
- 是否为了“高级感”堆叠形容词和对称句

AI 可以协助生产，但最终必须由编辑判断是否像真人写作。

## 10. 自动文学 Gate

代码中的 `JourneyLiteraryQualityAuditor` 必须检查：

- 正式编辑稿数量等于运行时 Journey 数量
- 每篇 4 个 section 与 4 组阅读支持完整
- 每篇有主角、叙事模式、情绪曲线与结尾模式元数据
- 主角在开场建立
- 通用时间／天气开场比例
- 保护式结尾比例
- 直接人物声音覆盖率
- 叙事模式是否重复
- 结尾模式是否重复
- 任意两篇中文内容的最高相似度
- AI 固定转折表达密度

发布门槛：

- severe = 0
- medium = 0
- 只允许少量不阻断的 light 优化建议
- 全部正式 Journey 必须存在于编辑稿注册表
- 自动 Gate 通过后仍须进行人工总编辑抽查

不得通过提高阈值、删除故事、删除测试或改变统计口径来规避失败。

## 11. 人工复审顺序

每次故事库变化后：

1. 完整阅读所有被修改故事。
2. 阅读修改故事前后相邻的至少五篇 Journey。
3. 检查是否创造新的开场、高潮或结尾模板。
4. 检查普通 Journey 是否又变成文化导览。
5. 检查特别 Journey 是否又依赖相同神秘物件。
6. 以 8、12、16 岁与成年人四个视角判断继续阅读意愿。
7. 检查 HSK／TOCFL 学习价值和自然中文。
8. 检查 Story、词语、Discovery、挑战与回忆是否一致。
9. 运行全库文学 Gate、内容 Gate、Flutter tests 与 Preview。
10. 若仍有 severe 或 medium，继续修改，不得进入发布或合并。

## 12. 维护规则

- 新增最佳实践时，同步更新本文、代码和测试。
- 改变文学 Gate 时，同步更新 auditor、测试、质量报告与 changelog。
- 新增 Journey 时，必须在同一个 PR 中增加正式编辑身份元数据。
- 作品集出现新模板化趋势时，优先修正全库，不只修正被发现的单篇。
- `main` 仍只能在 Founder 明确批准后合并。
